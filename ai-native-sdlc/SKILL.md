# AI 原生团队开发流程

你负责把用户意图转成可交接、可核验的工程交付。默认由当前 Agent 协调；人负责目标、取舍和项目规定的批准，Agent 负责整理、实现、核验与回报。面向用户使用中文，保留代码和技术标识。

## 先确定任务边界

1. 读取目标项目适用的 `AGENTS.md`、团队契约及其指定的真实命令、已有需求/计划和当前工作区状态。已有系统与约定优先，不凭课程示例猜测框架、人员、CI、接口或生产状态。
2. 明确本次目标、产物真源、当前阶段、已有授权、验收标准和实际阻塞。首次接入读 [团队接入](references/团队接入.md)；继续已有工作时复用原记录，不另起一套。
3. 用户要求仅讨论、仅计划、只读评审或暂停时，遵守该范围。已授权的常规开发持续推进；不要在每个阶段重复索要确认。只对会改变目标、验收、授权或难以撤销结果的分歧提问，同时继续不依赖该答案的工作。
4. 选择下面的流程深度，说明必要假设。模板按需取用，不批量生成空文件。

| 深度 | 何时采用 | 最小记录 |
| --- | --- | --- |
| 轻量 | 范围明确、易回退、无对外契约变化的小修复、文案或局部调整 | 现有工单/PR 的一个记录，或 [change.md](assets/templates/change.md)：目标、改动、验证、交付状态 |
| 标准 | 新功能、跨模块变更、多人接力或需要可审查设计的工作 | `intent.md`、`spec.md`、`plan.md` 及验证、评审记录；可链接已有真源，不重复抄写 |
| 增强 | 项目已认定的重要变更，如权限、持久化数据迁移、外部 API 兼容性或生产发布 | 标准流程加该项目要求的影响分析、批准证据、发布验证与回滚方案 |

轻量/标准/增强是记录深度，不是自动授予权限的级别。项目已有要求不得因选择轻量而省略；低影响修改也不应被强制套入完整文档链。

## 按当前阶段推进

只有进入相应阶段时才读 [阶段规范](references/阶段规范.md) 的对应段落。阶段是工作指引，不会自行创建后台作业或授权下一阶段。

| 阶段 | 要解决的问题 | 输出与进入下一步的证据 |
| --- | --- | --- |
| Plan：捕获意图 | 为什么做、服务谁、成功是什么、范围到哪 | 意图及来源；目标有负责人或明确的用户授权 |
| Design：需求与设计 | 行为、边界、接口与异常怎样定义 | 可验收规格；关键分歧已解决或明确阻塞范围 |
| Build：计划与实现 | 改哪些文件、按什么顺序、如何证明 | 可审查计划、代码与必要测试；计划偏离有记录 |
| Test：反馈与核验 | 行为是否满足规格，有没有回归 | 实际命令/运行/视觉证据，失败与未验证项明确 |
| Deploy：评审与发布 | 是否可合并、可发布、已发布并验证 | 按项目规则的评审决定、流水线结果、版本与环境证据 |
| Maintain：观察与改进 | 发布是否健康，下一轮改进来自哪里 | 指标/事故证据、新需求或回归用例，回到 Plan |

从已有阶段开始，不补造历史批准、测试结果或生产记录。用户只要求其中一段，就交付那一段的完整结果。

## 团队交接规则

- 每个工作项有一个协调责任人；每个并行任务明确输入版本、允许写入范围、输出、验收和接收方。使用 [handoff.md](assets/templates/handoff.md)。
- 多角色是职责，不等于必须启动多个 Agent。仅在运行环境允许且确有独立工作流时委派；共享文件、接口的连续决策由同一责任人串行处理。细则见 [协作与交接](references/协作与交接.md)。
- 已有多人改动不得回退。隔离检出也不能消除业务依赖；接口先由指定负责人定稿，再让使用方实现。
- 实现者自测与独立核验分开标记。没有独立核验资源时如实报告自测，不伪造一个 Reviewer 或 Verifier。
- 子 Agent 的“完成”是交接信息，协调者须检查实际差异、产物和证据后才确认对应阶段。

## 验证与完成规则

详细的反馈循环、证据分层、评审与 Agent eval 见 [验证与持续改进](references/验证与持续改进.md)。

1. 验证针对可观察行为和真实风险。缺陷优先复现，修复后按原验收重验；仅文案等低影响变更用相称的检查。不得为通过而删除失败用例、跳过必要检查或放宽断言。需求确有变化时说明依据，并让检查验证新契约。
2. 使用仓库中已确认的命令。UI 行为需要运行交互/视觉证据；第三方集成分别记录模拟、契约检查和实际服务验证。构建成功、HTTP 200 或命令退出码不能单独证明端到端可用。
3. 证据标明所验证的提交或工作区差异、环境、时间、命令/操作与结果。证据后有影响相关行为的新修改，重跑受影响检查，不沿用旧结果。
4. 持久化/外部写入结果不明时先查询回执或现状，不重复执行。已有重试规则按项目执行；没有新证据时停止同一失败循环，并说明受阻步骤。
5. Skill 是协作指引。CI、分支保护、权限和 hooks 是否强制生效须另有执行证据；本 Skill 不替代它们，也不自动修改这些配置。
6. 区分“文档已形成”“本地实现已验证”“已独立核验”“可评审”“已合并”“已发布”“发布后已验证”。只报告证据支持的状态；本次仅要求计划时，计划交付即可完成本次任务。

## 记录和收尾

保持每类产物只有一个真源。已有工单、设计工具或知识系统为真源时，Markdown 只存链接、版本和必要工作上下文；项目已有路径优先。无约定时，可在 `docs/changes/<work-id>/` 保存标准工作项，在 `docs/team-sdlc.md` 保存团队契约。

只创建当次需要的模板：[意图](assets/templates/intent.md)、[规格](assets/templates/spec.md)、[计划](assets/templates/plan.md)、[验证](assets/templates/evidence.md)、[评审政策](assets/templates/REVIEW.md)、[发布](assets/templates/release.md)、[事故](assets/templates/incident.md)。复制后填入真实内容；未知项写明影响，未执行项保留未执行，不把模板当成完成记录。

最终回复先给交付结论，再给产物入口、验证结果与限制、尚需的实质决定。若需批准，指出批准的具体产物版本、动作和依据，先完成所有已授权准备工作。清理本次无继续用途的临时文件。

课程来源、14 课对应关系及团队化改编见 [课程映射](references/课程映射.md)；仅在查证来源或修订本 Skill 时读取。

# 协作与交接

## 责任分配

下表描述职责。同一人可承担多个职责；人员姓名与批准资格来自目标团队契约。实现者自行检查不得称作独立核验。

| 职责 | 核心输入 | 负责交付 | 判断边界 |
| --- | --- | --- | --- |
| 协调者 | 用户目标、工作项与当前证据 | 阶段判断、依赖安排、交接、整合与最终报告 | 验证接收结果，不替其他批准人签字 |
| 产品负责人 | 用户/业务证据 | 意图、范围、优先级、成功标准 | 决定产品取舍，技术事实交给证据确认 |
| 工程负责人 | 意图、规格、仓库事实 | 方案、接口、实现顺序与技术取舍 | 重大变更按项目现有规则处理 |
| 实现者 | 明确版本的规格、计划和任务包 | 允许范围内的代码、测试、自测证据 | 不扩大任务范围，不改写验收来掩盖失败 |
| 核验者 | 同一版本的规格、产物和验收条件 | 独立运行结果、失败复现和覆盖缺口 | 默认不修改实现；发现交回实现者 |
| 评审者 | 差异、规格、计划、验证证据 | 具体问题、严重性与评审结论 | 批准能力依项目规则，不由角色名称授予 |
| 发布/运行负责人 | 评审结论、候选版本、部署记录 | 环境限定的发布、恢复与观察结果 | 按现有授权和运行手册行动 |

## 是否委派

先遵守宿主平台与项目对委派的限制。有真正独立的任务、明确输出且委派能降低等待或提高独立判断质量时才使用子 Agent。只改一个文件、共享状态连续变化或主任务本身很短时，由当前 Agent 完成。

适合的例子：一个 Agent 只读核查接口兼容性，另一个只读核查用户交互；接口已定稿后，两个互不重叠模块各自实现。共享 API 尚未确定时，先由一个负责人处理接口，不让多个 Agent 各自发明契约。

使用子 Agent 不需要为每项职责新建用户聊天。只有用户要求新聊天时才创建持久聊天；授权缺失时不向其他已有聊天派发消息。

## 工作区和所有权

每个任务使用 [handoff.md](../assets/templates/handoff.md) 说明：

- 唯一工作项/任务标识，目标及验收编号。
- 仓库、分支/检出路径、基础提交和输入版本；工作区未提交时，附差异文件列表或摘要及其指纹。
- 可写路径/模块、只读依赖、禁止改动的已冻结资产。
- 依赖任务、整合顺序、接收人和结果检查方式。
- 允许工具、外部动作、预算或停止条件；未知的权限不能从任务名称推断。

多写入任务优先使用独立分支/工作树。共享同一检出时按文件/模块划定互斥写入范围，并明确告知每位实现者：你不是唯一改动者，不得回退别人修改，要兼容已发生的变化。发现范围重叠，先协调再继续。

## 接收与整合

发送者提供实际改动、检查输出、已知缺口和输入版本。接收者检查文件是否存在、差异是否落在范围内、验证是否针对当前产物，并记录接收状态。空回复、任务已排队或子 Agent 自报成功都不等于接收完成。

整合者确认各结果依赖的接口一致，再按计划合并。只接受已理解的差异，不用强制覆盖解决冲突。整合改变相关行为时重跑对应检查；不要让每个子任务的局部通过代替整体结果。

若上游规格或接口变化，显式标记受影响交接已过期，通知获授权的协作对象或更新共享记录；接收者按新版本继续。无权发送消息时在本会话报告待交接项。

## 可复制的角色任务卡

将方括号替换为目标任务的真实信息；它们是提示词模板，不会自动注册 Agent。

### 实现者

```text
你负责 [任务及允许修改的模块]。读取 [规格/计划的路径与版本]。
完成 [验收编号]，使用项目确认的 [检查入口] 验证。
你不是唯一改动者，不得回退其他人的修改；发现冲突先报告并协调。
不要改动 [边界]。返回实际差异、运行命令/结果、产物版本和剩余问题。
遇到 [明确停止条件] 停止依赖步骤，继续不受影响且已授权的工作。
```

### 独立核验者

```text
基于 [规格及验收条件]，独立核验 [当前版本和工作目录]。
读取适用项目规则，执行允许的检查，关注本次行为和最近的邻接流程。
不要修改实现或以实现者结论代替证据。返回实际观察、证据位置、
失败复现以及未覆盖项；将自测、模拟与实际运行分开。
```

### 评审者

```text
只读检查 [差异/PR/提交]，按项目评审政策核对 [意图、规格、计划]。
输出可定位且有因果依据的问题，列严重性、影响、证据和建议。
若未发现问题，说明实际检查范围与验证限制，不推断生产状态。
```

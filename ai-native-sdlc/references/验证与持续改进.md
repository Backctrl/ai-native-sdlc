# 验证与持续改进

## 可用证据支持什么结论

| 证据 | 可以支持 | 不能单独支持 |
| --- | --- | --- |
| 文件、差异、静态检查 | 产物存在、特定结构/规则符合 | 用户流程可用、第三方连接成功 |
| 本地测试与构建 | 被覆盖的逻辑或构建在该环境通过 | UI 视觉正确、实际服务契约吻合、生产已发布 |
| 模拟服务或测试替身 | 在设定条件下的集成逻辑 | 真实账户权限、远端数据写入或响应成功 |
| 浏览器/客户端交互与视觉记录 | 所操作流程、状态与渲染符合验收 | 未操作的流程和其他设备均正确 |
| 真实外部服务请求及读回 | 该环境/身份下的调用与持久化结果 | 其他权限、其他版本、生产全量可靠性 |
| 部署回执和版本查询 | 指定版本部署到了指定环境 | 发布后功能与健康已验证 |
| 发布后目标行为和健康信号 | 对应观察窗口内的运行表现 | 永久无缺陷或所有业务指标提升 |

每份证据绑定实际时间、环境与版本。未提交的工作区记录基础提交、改动文件及差异摘要/指纹；不伪造提交 SHA。测试命令没执行、输出缺失、条件不满足时标记未验证，而不是补写一个看似成功的结果。

## 反馈循环

1. 从验收条件找最快能证伪实现的检查。修复缺陷时，先保存能说明原问题的失败证据；没有稳定复现则写明原因。
2. 对相关实现做小步修改并执行检查。失败时先区分产品缺陷、检查错误与环境问题，依据实际输出调整。
3. 检查是否在验证预期行为，而不是重复实现逻辑。不要删断言、加无依据的跳过或把异常吞掉来通过检查。
4. 完成当前任务要求的检查，记录原始输出的路径或链接。影响小且可逆的改动可以采用读回、页面观察或现有检查，不机械新增测试。
5. 新改动只使受影响的证据失效；重跑对应检查。已经通过且未受影响的检查不必重复。

命令失败且没有新的诊断依据时，停止相同尝试并报告阻塞点。外部写入超时先查询任务状态或读回结果；无法确认就标记结果未知，不能自动当作失败重发。

## 独立核验与评审

独立核验者从规格和验收条件出发，在新的上下文中检查当前产物。实现者可以提供启动方法和必要环境信息，但不能用“我已经通过了”代替核验者的实际观察。

评审按项目定义的严重性分级；项目没有标准时，可使用下面的描述作为本次报告解释，不自动写入组织政策：

- 阻断：有证据会造成关键行为错误、数据损坏/泄露或违反已明确的必要契约。
- 重要：可复现的功能缺陷、回归或验收缺口，需要处理后再宣称相应阶段完成。
- 建议：不影响当前验收的可维护性或表达改进，避免大量风格噪声。

每条发现写位置、触发条件、实际与预期差异、影响和证据；无法确认的写成待核实风险。CI 已充分证明的问题避免重复罗列，但不能因为“CI 理应覆盖”就忽略实际失败。

## 软件测试和 Agent eval

软件测试验证产品行为。Agent eval 验证 Agent 在给定任务、工具、规则和权限下是否采取合适行动，交付是否正确；两者不能互相替代。

从近期有已接受结果的真实任务开始，先建立小而有区分力的样本，再按团队成本扩充。课程的 20–50 个任务是扩展建议，不是启动前置条件。

每个 eval 保存：原始请求、固定输入/版本、隔离环境、允许副作用、实际模型/工具/Skill 版本、验收方法、预算与结果证据。不要把期望答案塞给执行 Agent；用产物、工具行为和真实检查判定。

当团队契约、Skill、提示词、工具权限、模型或 hooks 改变时，运行受影响的 eval；涉及行为稳定性的变更与既有基线比较。必要时对存在随机性的任务重复运行，报告次数与波动，不从一次成功推断稳定通过率。

优先用确定性检查判断文件、接口、测试和越界副作用；语义质量可由独立评审补充。失败样本要能区分产品缺陷、Agent 决策问题、环境故障和验收标准错误。

CI 接入需要团队已有运行器、预算、结果存储与权限。先给可审查接入差异，再按授权配置；本 Skill 未内置凭据或任何后台调用。Agent 创建的产物应继续走项目的审查路径。

## 维护流程知识

重复出现且有证据的误解，适合成为规则修订候选。先判断它属于项目事实、可复用流程还是单次例外，再更新对应真源；不要把每次失败都升级为全局禁令。

每次修订说明来源事件、改变的决定和验证方法。团队规则的正式变更按其已有流程采纳；没有采纳记录时标为候选，不能宣称团队已生效。

衡量改进时使用可取得的数据：交付耗时与评审等待、首次检查通过率与返工、发布失败与恢复耗时。注明定义、样本和时间窗口。没有历史基线时建立基线，不编造“效率提升百分比”。

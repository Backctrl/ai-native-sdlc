# 阶段规范

按当前阶段阅读。下列模板字段是信息清单，可映射到团队既有工单、设计记录或 PR；不要为了文件齐全重复维护同一事实。

## Plan：捕获意图

输入来自用户原话、现有工单或有时间范围的真实告警。记录来源、受影响用户与系统、现状、期望结果、约束、范围外事项、成功证据和开放问题。区分已知事实、待核实假设及产品取舍，不替用户编造业务收益或指标。

输出使用 [intent.md](../assets/templates/intent.md)。用户已经给出清晰目标与执行授权时，直接记录这份授权，不为填写模板要求重复确认。需要产品负责人接受的项目，沿用原有接受方式。仅有想法讨论时不得写成已批准需求。

进入 Design 的条件：目标与范围足够明确；会改变成功标准的分歧已解决。非关键问题可带入后续记录并指定责任人。

## Design：需求与设计

读取意图、现有实现、设计系统以及本次实际相关的政策。规格描述用户能观察到的行为、主要流程、异常路径、权限与数据边界、接口兼容性和验收条件。不要罗列与任务无关的政策。

给验收条件稳定编号，如 `AC-01`，写清输入/操作/期望。UI 项补关键状态和原型真源；接口项补请求、响应、错误与兼容性；数据项补约束与迁移影响。无法访问的外部契约标明未验证，不按猜测实现不可逆操作。

输出使用 [spec.md](../assets/templates/spec.md)。当存在实质方案分歧，展示各方案对目标、成本或风险的影响并推荐一个；没有实质分歧时用现有约定作决定。

进入 Build 的条件：关键行为可验收、依赖已明确，并满足项目现有设计决策要求。合规工具、设计工具中的真源保持不变，Markdown 引用对应记录与版本。

## Build：先计划，再实现

先读现有代码、命令入口、相关测试与 Git 差异。计划至少把验收条件映射到改动模块、实施顺序、依赖和验证方法。采用 [plan.md](../assets/templates/plan.md)；轻量任务可在单条工作记录里完成。

用户要求先审阅计划时，只完成读取和计划产物，不开始实现。用户已授权范围明确的实现时，计划作为可审查记录后继续执行；项目有额外批准要求的，按该要求处理。

并行前识别共享接口、共享文件和依赖，指定整合人。不能独立交付的步骤串行。实现中出现常规可逆调整，同步计划和原因后推进；若触及新的目标、对外契约、批准权限或状态规则，则先展示差异并按项目要求处理决定。

实现使用最短有效反馈循环：修改相关部分 → 运行受影响检查 → 根据真实失败修正。计划中的完成勾选要能指向实际产物或证据。

进入 Test 的条件：实现覆盖本次约定范围，现有自测已记录，缺口明确。实现者说“已完成”不替代实际核验。

## Test：验证行为

按 `AC` 编号建立证据映射，选择单元/集成/交互/视觉/实际服务验证。先验证此次变化，再检查最相关的邻接流程。项目要求的检查都需运行；检查通过后没有新变化或新疑点，就不扩大无关测试。

缺陷应尽可能保存修复前的失败证据与修复后的对应成功证据。未能复现时写明条件和限制，不声称已证明根因。测试本身有错误时，提供独立依据后修正，不为绿色结果迁就实现。

使用 [evidence.md](../assets/templates/evidence.md)。重要或复杂变更可在允许委派的环境使用独立核验者；该角色只读实现并运行允许的检查，发现问题交回实现者处理。

进入评审的条件：必要验收有当前版本证据；未通过、未执行和不适用项有具体解释。未执行的必要检查不得算通过。

## Deploy：评审、合并与发布

先依据已生效的评审政策，检查行为与逻辑、相关安全与权限边界、规格/计划符合性。若要建立政策，可参考 [REVIEW.md](../assets/templates/REVIEW.md) 并按项目要求采纳。评审发现必须能定位到当前代码或行为，不汇总无证据的猜测。

处理评审意见后，更新受影响检查，检查最终差异是否仍符合意图。PR 描述链接需求、计划、验证和遗留问题。Agent 的评审结果为证据，批准主体与合并方式以项目规则为准。

合并、发布和发布后验证分别记录。发布前准备版本/提交、目标环境、变更影响、健康检查及适用的回滚方法；需要批准时，展示这份具体发布对象再请求。已有授权可用，不能凭一句“测试通过”扩展生产权限。

使用 [release.md](../assets/templates/release.md)。执行后读取真实流水线/部署回执，确认部署版本与目标环境；再验证目标行为和健康信号。只有启动成功或流水线排队，不得写“已发布并验证”。

若发布失败，先判断是否已产生外部副作用，按项目运行手册处理或停止依赖链。回滚后重新核验状态；不能仅凭回滚命令退出码宣称恢复。

## Maintain：把发现送回需求

读取实际时间窗口、指标定义、数据来源和已定义的阈值。检测使用可解释的规则或确定性脚本；Agent 负责诊断、关联变更和提出行动。课程的 `1σ/2σ/3σ` 是示例，不能直接当作目标系统阈值。

异常形成 [incident.md](../assets/templates/incident.md)，包含影响、时间线、观察事实、假设、行动回执和恢复验证。后续工作形成新的意图或原工作项的关联任务，保留双向链接。

生产缺陷补相称的软件回归检查；由 Agent 指令、工具使用或协作失败造成的问题，再加入 Agent eval。复盘中的团队规则变更先提供依据和差异，按规则真源的更新方式采纳。

指标建议从团队现有数据中选择：从意图到交付的耗时、评审等待、首次检查通过率、返工率、变更失败率或恢复耗时。速度和质量一起看，不用 Agent 调用量或生成代码行数代替成果。
